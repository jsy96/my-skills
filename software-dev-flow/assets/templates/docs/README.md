# docs/ —— 集中内容层

软件项目需要统一查找的**实际内容产出**写在这里:需求、架构、跨模块契约、测试策略、部署手册、评审和交付说明……

- 单仓多子项目仍共用这一份根级 `docs/`,按需建子目录:
  - `requirements/` — 需求、用户故事、验收条件
  - `architecture/` — 总体架构、技术选型理由
  - `contracts/` — **API、事件、数据模型、跨模块接口的真相源**(契约先行:先改这里,再改代码)
  - `modules/<module>/` — 只描述某个子项目、但需要统一发现的说明
  - `testing/` — 测试策略、覆盖率基线、测试报告
  - `runbooks/` — 部署、发布、回滚手册(发布步骤的真相源)
  - `reviews/` — 跨模型评审结论
- 控制层(charter / plan / 任务卡 / 交接 / 变更日志)不放这里,放 `flow/`。
- 子项目目录默认放代码、测试和构建配置,不主动重复建立文档体系。
- 已有 README、生成文档或必须紧贴代码维护的说明可以留在子项目里;在下方索引其真实路径,不要为了集中而搬动。
- 判据:需要**统一发现的知识、契约和交付说明** → 根级 `docs/`;**协调 / 推进项目** → 根级 `flow/`;代码 → 对应子项目。
