# 多子项目结构

> 当一个总体项目同时包含前端、后端、共享包、服务或工具时读本文件。目标是先划清项目边界,再决定协作文件放在哪一层。

## 1. 先判断项目边界

不要按文件夹数量判断项目数量。看这几个事实:

| 现场 | 归类 | 协作结构 |
|---|---|---|
| 多个代码目录共用一个仓库、产品目标、版本节奏和根级构建配置 | 单仓多子项目(monorepo) | 根级一套 `flow/`、`docs/`、hook;子项目只建局部入口 |
| 子目录有自己的 `.git`,或明确独立发布、独立权限、独立生命周期 | 独立项目 / 独立仓库 | 每个仓库各自一套完整协作骨架 |
| 一个主应用带少量内部包、脚本或工具目录 | 单体项目 + 子模块 | 根级一套协作骨架;仅有独立职责的模块才建局部入口 |
| 多个独立仓库另有一个集成或产品总控仓库 | 多仓总体项目 | 各仓库各自管理;总控仓库可另建一套只管跨仓协调的 `flow/`、`docs/` |

辅助线索:workspace 配置(`pnpm-workspace.yaml`、npm/yarn workspaces、Cargo workspace、Go workspace)、根级构建编排、共享 CI、统一发布脚本和嵌套 `.git`。`node_modules/`、`dist/`、`build/`、`venv/`、临时目录和普通工具目录不是子项目。

拿不准时,先把识别到的候选子项目和判断依据列给用户确认,不要直接铺文件。

## 2. 单仓多子项目的默认结构

```text
总体项目/
├── AGENTS.md                        # 总体运行时合同(含门禁命令区)
├── CLAUDE.md -> AGENTS.md
├── flow/                            # 唯一总体控制层
│   ├── charter.md
│   ├── plan.md
│   ├── 进展.md
│   ├── decisions.md
│   ├── 踩坑记录.md
│   ├── releases.md                  # 变更日志
│   ├── tasks/
│   └── 规范/
├── docs/                            # 默认集中管理项目文档
│   ├── README.md
│   ├── requirements/                # 需求、用户故事、验收条件
│   ├── architecture/                # 总体架构、技术选型理由
│   ├── contracts/                   # API、事件、数据模型、跨模块接口(真相源)
│   ├── modules/
│   │   ├── frontend/
│   │   └── backend/
│   ├── testing/                     # 测试策略、覆盖率、测试报告
│   ├── runbooks/                    # 部署、发布、回滚手册
│   └── reviews/                     # 评审结论
├── frontend/
│   ├── AGENTS.md                    # 局部合同(含本模块门禁命令)
│   ├── CLAUDE.md -> AGENTS.md
│   └── <源码、测试、构建配置>
├── backend/
│   ├── AGENTS.md
│   ├── CLAUDE.md -> AGENTS.md
│   └── <源码、测试、构建配置>
└── .hooks/ .claude/ .codex/         # 只装在总体项目根
```

这里的关键不是目录名,而是**一个总体项目只有一个控制面**。所有总体目标、计划、任务卡、决策、问题、交接和变更日志进入根级 `flow/`;所有跨模块或需要统一查找的知识、契约与交付说明进入根级 `docs/`。

## 3. 文档统一管理的边界

默认把文档收口到根级 `docs/`,再按主题或模块分目录:

- 需求、总体架构、发布方案、评审报告 → `docs/requirements/`、`docs/architecture/`、`docs/reviews/`
- API、事件、数据模型、前后端口径 → `docs/contracts/`(**契约先行**的落点)
- 测试策略、覆盖率基线、测试报告 → `docs/testing/`
- 部署 / 发布 / 回滚手册 → `docs/runbooks/`
- 只描述某个子项目、但仍需要统一发现的说明 → `docs/modules/<module>/`
- 总体推进、任务状态、交接、决策、踩坑和变更日志 → `flow/`,不进 `docs/`

子项目目录默认放源码、测试、构建与运行配置,不主动再建一套 `docs/`。以下代码邻近文档可以例外保留在子项目里:

- 已存在且由该工具链或社区约定使用的 `README.md`
- 随代码生成的 API 文档、迁移说明或组件文档
- 必须和本模块代码在同一次变更中维护的开发说明

例外文件不需要为了"集中"而搬家;在根级 `docs/README.md` 加一条索引即可。

## 4. 子项目局部入口

每个有独立职责的子项目都建立:

```text
<module>/AGENTS.md
<module>/CLAUDE.md -> AGENTS.md
```

用 `assets/templates/MODULE_AGENTS.md` 生成,替换占位符,并填入从该模块配置里**探测到的**构建 / 测试 / lint 命令。局部入口只写:

- 本模块负责和不负责什么
- 代码、测试、构建、lint 命令入口(本模块门禁命令)
- 模块内部的非显而易见约定与禁区
- 指向根级 `flow/`、`docs/` 和跨模块契约的路径

不要在局部入口重抄总体 charter、计划、进展或通用约定。根级规则管整体,局部规则只补充当前目录范围;跨模块契约仍以根级 `docs/contracts/` 为真相源。

若已有局部 `AGENTS.md` 或 `CLAUDE.md`,按初始化 SOP 非破坏合并。两个文件内容不一致或不能安全建软链时,列为冲突项让用户确认,不要覆盖。

## 5. 什么时候给子项目完整 `flow/`

只有子项目实际上已经成为独立项目边界时才这样做,通常至少满足一项:

- 自己是独立 Git 仓库
- 独立版本、发布和回滚(有自己的 releases / changelog)
- 独立团队或权限边界
- 独立目标、计划和交接历史

此时应在该独立仓库根运行完整初始化。若还需要总体协调,用一个上层总控仓库记录跨仓里程碑、契约和集成交接,不要把各仓内部任务重复抄过去。

## 6. 初始化输出必须说明什么

执行前的确认清单至少写明:

1. 识别出的项目边界和依据。
2. 哪些目录被视为独立职责子项目。
3. 根级会创建或合并哪些文件;探测到的门禁命令及出处。
4. 每个子项目会创建或合并哪些局部入口。
5. 明确声明不会创建哪些内容,例如不在子项目重复建 `flow/`、`docs/`、hook,不移动现有文档。
