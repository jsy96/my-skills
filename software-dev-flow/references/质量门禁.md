# 质量门禁

> 定义"一张任务卡什么叫完成"(DoD)、四道门怎么跑、红了怎么办。
> 门禁是软件版流程区别于通用协作流程的核心:协作骨架保证"不丢上下文",门禁保证"不交付坏的代码"。

---

## 1. 四道门(完成 = 全绿)

| 门 | 内容 | 命令真相源 |
|---|---|---|
| ① 构建 | 项目能从干净检出构建成功 | 根级 `AGENTS.md` 门禁命令区「构建」 |
| ② 测试 | 全量测试通过;**本轮新增 / 修改的行为有对应测试** | 门禁命令区「测试」 |
| ③ 静态检查 | lint / typecheck / formatter 无错误(项目没配则此门免) | 门禁命令区「静态检查」 |
| ④ 评审 | **换另一个模型评审**(审稿模型 ≠ 产出模型)PASS | 结论写 `docs/reviews/` 或任务卡 |

- 门禁命令区是**唯一真相源**:初始化时从项目配置探测填入;构建方式变了,先改命令区再跑门。
- 命令区标 TODO 的门(未探测到),跑门禁前先请用户补命令,不要猜。
- 四道门全绿(或某门经用户明确豁免)才允许:任务卡标「完成」、分支合并、收工交接。

## 2. 门禁状态怎么记

- **任务卡**「状态」字段:`待办 / 进行中 / 待评审 / 门禁未过 / 完成`。
- **进展条**「门禁状态」字段:逐门标 ✓ 或 ✗,例如:
  - `构建 ✓ · 测试 ✓(34 passed)· lint ✓ · 评审 PASS`
  - `构建 ✓ · 测试 ✗(2 failed,见下)· lint 未跑(命令 TODO)· 评审 未到`
  - 本轮没改代码:`本轮无代码变更`。
- **如实记录是铁律**:未跑就写未跑,不许装绿;失败的测试名 / 报错摘要写进进展条,细节给文件路径或日志路径。

## 3. 红了怎么办(不许绕过)

1. **修**:定位根因,从根本解决,不打补丁(打补丁的诱惑本身就是信号)。
2. **回滚**:这一棒方向错了就回退分支,把原因写进 `flow/踩坑记录.md`,别留半成品过夜。
3. **豁免**:确实要带病收工(时间盒到了 / 依赖外部修复)→ 明确向用户说明哪道门没过、为什么、什么时候补,**用户确认后**才能标「完成(豁免:… )」,豁免原因同时写进进展条和 `flow/releases.md`(若将发布)。
- 严禁:注释掉失败的测试、降低断言、只跑改过的文件冒充全量、跳过评审直接合并。

## 4. 评审(第四道门)怎么做

- 模式:Codex 审 Claude 的产出,或反之;同一棒里**产出者不能当自己的审稿人**。
- 喂给审稿方:任务卡(验收标准)+ 改动(diff / 文件路径)+ 契约文档路径。**带上门禁前三道的结果**,别让审稿方重跑一遍才发现构建是红的。
- 审稿方输出:PASS / FAIL + 问题清单(按严重度)。FAIL 的问题修完**复审**,不是口头说改了就算。
- 审查清单(供审稿方展开):
  - 正确性:逻辑、边界条件、错误路径
  - 契约一致性:实现与 `docs/contracts/` 是否一致
  - 测试:新行为有测试吗;测试测的是行为还是实现细节
  - 安全:输入校验、注入、密钥硬编码、权限
  - 可维护性:命名、重复、死代码、有没有更简单的做法
- 结论落 `docs/reviews/<日期>-<任务或主题>.md` 或任务卡,进展条给路径。

## 5. 与分支 / 合并的关系

- 每任务一分支(`<type>/T<编号>-<短描述>`),门禁在分支上跑。
- 全绿 → 合并(merge / squash 按项目习惯)→ 任务卡「完成」→ 归档。
- 合并后主线再跑一次 ①②(集成门),防止任务各自绿、合起来红。
- 主线红了 = 最高优先级事件:先修主线或回退合并,再开新任务。

## 6. 什么时候门禁可以轻量

- 纯文档棒(docs / flow 文件):免 ①②③,评审可简化为交叉读一遍;进展条标「本轮无代码变更」。
- 探索性 spike(技术验证):允许带 ✗ 收工,但**结论必须落 `docs/` 或踩坑记录**,spike 代码默认不合并主干——要么重写成带测试的实现,要么删掉留文档。
- 以上是"轻量",不是"没有":状态如实记录这条不豁免。
