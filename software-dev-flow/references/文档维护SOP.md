# 文档维护 SOP

> 元规则:规定 `AGENTS.md` 体系该写什么、不该写什么、谁在什么时候写、写到哪一层、怎么写。
> 目的:让 Claude Code 和 Codex 按同一套标准维护文档,避免漂移、膨胀或遗漏。
> **适用于任何软件项目,不绑定技术栈。**

---

## 1. 写入标准(什么该进文档)
只沉淀**非显而易见、看产物本身看不出来**的内容:
- **设计哲学 / 心智模型**:把这件事理解成什么(例:"任务型而非聊天型")
- **关键决策 + 背后的"为什么"**:不是"我们用了 X",而是"为什么选 X、否定了 Y"
- **方向定位**:目标对象、核心命题、一句话定位
- **环节 / 模块间的契约**:交接口径、字段约定、依赖关系(正文落 `docs/contracts/`,原则进 `AGENTS.md`)
- **门禁与环境的"为什么"**:为什么这条门禁这么严、为什么 CI 这么配;**命令本身**写门禁命令区并保持同步
- **废弃 / 禁区**:哪些东西不要动、哪些做法不要再用
- **外部参考资料**:链接、调研、竞品、范例(带日期和用途)
- **非显而易见的约定**:违背常规习惯的项目特例(如"必须 /utf-8 编译""发版只走 runbook")
- **重要历史节点**:重大调整、废弃决策(带绝对日期,如 `2026-03`)

## 2. 不写标准(什么不进文档)
- **看产物本身就知道的**:文件清单、目录结构、内容本身
- **版本历史能查到的**(git log / blame 等):谁改的、改了啥
- **一次性状态**:当前 TODO、临时进度(在 `flow/` 里,不进 `AGENTS.md`)
- **通用常识 / 最佳实践**(除非项目有特例)
- **个别问题的修复细节**(修复本身在产物、测试和提交记录里)

## 3. 触发时机(什么时候写)
出现以下信号时**主动提议**写入(不擅自写,列修改点等确认):
- 用陈述句描述了一条新的**设计哲学 / 心智模型 / 方向定位** → `AGENTS.md`
- 本轮做了**结构 / 方案 / 契约调整**(新增模块、改接口、废弃某部分)→ `AGENTS.md`(原则)+ `docs/contracts/`(正文)
- **构建 / 测试 / lint 命令变了**(换构建系统、加测试框架、改脚本名)→ 同步 `AGENTS.md` 门禁命令区,子项目变了同步局部入口
- **环境或发布方式变了**(新部署目标、CI 改版)→ `docs/runbooks/` 回填,入口处指一句
- 分享了**需要持续参考的外部资料** → `AGENTS.md`(根级引用索引)
- 出现"**以后都这么办 / 不要再 X / 记住 Y**"的长期约定 → `AGENTS.md`
- 每轮结束前主动按以上核对。hook 只是一层保险,没 hook 的会话也要自觉过一遍。
- (若项目有 UI / 设计工作,另有一条 → `DESIGN.md`,见 §7)

## 4. 分层归属(写到哪一份)
### 4.1 建立原则
每个总体项目边界建立一份根级 `AGENTS.md`,并让根级 `CLAUDE.md` 指向它。**单仓多子项目中,每个有独立职责的子模块 / 子项目都建立局部 `AGENTS.md` + 同目录 `CLAUDE.md` 软链**;纯工具、构建产物和杂项目录无需单建。

规则入口可以分层,控制层和内容层默认不分裂:总体目标、计划、交接、决策和变更日志仍集中在根级 `flow/`;项目文档与契约默认集中在根级 `docs/`。多子项目的完整结构见 `多子项目结构.md`。

### 4.2 各层职责
| 层级 | 写什么 |
|---|---|
| **根级 `/AGENTS.md`** | (1) 跨模块的哲学、定位、整体布局、通用约定;(2) **门禁命令区**(构建 / 测试 / lint 真实命令);(3) 从踩坑提炼出的**禁区 / 约定**(详细问题日志在 `flow/踩坑记录.md`);(4) 对外部资料、子模块文档、可选 `DESIGN.md` 的引用索引 |
| **子模块 `<module>/AGENTS.md`** | 仅限本模块的职责边界、**本模块**命令入口、心智模型、内部约定和模块级禁区——**不跨边界写别的模块,不复制总体计划** |
| **根级 `/docs/`** | 需求、架构、跨模块契约、测试策略、runbook、评审报告;按 `contracts/`、`modules/<module>/` 等子目录集中组织 |

原则:**规则就近,文档集中**。仅影响某个模块的运行规则写局部 `AGENTS.md`;跨模块规则写根级 `AGENTS.md`;知识和方案默认写根级 `docs/`。已有 README、生成文档或必须紧贴代码维护的说明可以留在模块内,但根级 `docs/README.md` 应给出索引。

> 命名:根级和子模块都以实体 `AGENTS.md` 为两端共用真相源,同目录 `CLAUDE.md` 软链到它。Windows 无法安全建软链时复制一份,并在后续更新时同时校验两份内容。

## 5. 操作流程(怎么写)
1. **识别**:出现触发信号
2. **归属**:判断进哪一层
3. **提议**:列出具体修改点(加在哪节、几行),等确认
4. **写入**:确认后修改目标层的实体 `AGENTS.md`;同目录 `CLAUDE.md` 是软链时自动同步。知识或方案写入根级 `docs/` 的对应目录
5. **保持精简**:能一行不写三行;非显而易见才留;过期内容顺手删

## 6. 同步更新(跨层变更时)
一次变更跨多层时(如改跨模块契约、心智模型演进),**相关各层都要同步更新**——只改一处会让另一处迅速过期。
- 改根级契约 → 同步涉及的子模块文档
- 改子模块心智 / 废弃策略 → 更新该模块 `AGENTS.md`;若影响跨模块理解,根级补一条
- 改跨模块接口 → 更新根级 `docs/contracts/` 真相源,再同步涉及模块的入口指针
- 改构建 / 测试 / lint 命令 → 根级门禁命令区与受影响模块的局部命令区**同轮**更新
- 发现某层过期,顺手修或删
- 若用了 `DESIGN.md`,它与 `AGENTS.md` 相互引用处两侧同步
原则:**文档同步跟着变更走**,一轮里改完就顺手把文档改完,不拖到下一轮。

## 7. 设计 / 创意类内容 → `DESIGN.md`(单独成文,可选)
设计、视觉、创意方向的决策**不进 `AGENTS.md`**,归 `DESIGN.md`;**仅当项目有 UI / 设计 / 创意工作时启用**,纯后端 / 库 / 工具项目可不建。

写什么:设计方向决策 + 为什么、外部视觉参考(带日期与用途)、设计系统 / 风格规范来源、重大设计历史节点(带绝对日期)。
不写什么:工程 / 方案 / 技术决策(→ `AGENTS.md`)、产物本身、一次性评审意见。
边界口诀:"为什么这么**做**(方案 / 结构)→ `AGENTS.md`;为什么这么**呈现**(设计 / 视觉)→ `DESIGN.md`。"
维护流程同 §5;`AGENTS.md` 引用索引里指一句向 `DESIGN.md`,相互引用处两侧同步。

## 反例速查
- ❌ "今天修了一个小问题" → 修复细节,不写(踩坑记录里记,见 `flow/踩坑记录.md`)
- ❌ "某文件里有某字段" → 看产物就知道,不写
- ❌ "跑测试用 npm test" → 命令进门禁命令区,不进知识区
- ✅ "X 模块是 A 心智而非 B,2026-03 从旧方案迁移" → 只影响 X 时写 `X/AGENTS.md`;影响总体理解时根级补索引
- ✅ "前后端新增某字段口径用于某用途" → 契约正文写根级 `docs/contracts/`,跨模块原则写根级 `AGENTS.md`

## 8. 文档自检 Hook
每轮结束的自检由 Stop hook 兜底。**配置与说明见 `hook机制.md`**,此处不重复。

## 9. 原则
1. **产物本身是真相的唯一来源**(文档只补"看产物看不出来的为什么")。
2. **解决问题从根本上解,不打补丁。**
