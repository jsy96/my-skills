# 开发工作流程

> 六段式软件开发生命周期 + 四个核心机制 + 目录归属。这是"活儿怎么流动"的详规。

---

## 六段式主循环(每个任务走一遍)

### ① 立项(需求)
填 `flow/charter.md`:目标 / 范围(做什么 + 不做什么)/ 约束 / 成功标准 / 角色,外加**技术栈与运行环境、质量基线**(测试框架、覆盖率要求、CI)。
需求细节(用户故事、验收条件)落 `docs/requirements/`。这是所有 Agent 开工要读的第一份;模糊目标先在这里钉死。

### ② 设计与拆解(契约先行)
- 出 `flow/plan.md`:里程碑 + 任务拆解(每个任务标:负责角色、输入、产出落哪、验收标准、分支名),你确认。
- **计划即契约**——要偏离,先改 `plan.md` 再动手。复杂任务先用 Plan 模式出书面计划。
- 跨模块接口(API / 事件 / 数据模型)**先落 `docs/contracts/`** 并确认,再排实现任务。契约是模块间唯一的真相源。

### ③ 实现(每任务一分支)
每个终端一个角色,读对应任务卡 `flow/tasks/T<编号>-<描述>.md` 开工。
- **每任务一分支**:`<type>/T<编号>-<短描述>`(如 `feat/T03-用户登录`、`fix/T07-登录超时`),完成过门禁后合并。
- 可独立的任务并行(git worktree / branch 隔离)。
- 小步、勤检查点。方案产出落根级 `docs/`;代码落对应子项目目录或单体项目的 `src/`,别只留对话里。
- 实现中发现契约有缺口 / 错误 → 回填 `docs/contracts/`,再继续(不要绕开契约硬写)。

### ④ 测试验证(同棒交付)
- **新代码与对应测试在同一棒交付**,不留"以后补测试"。
- 修 bug:先写一条能复现该 bug 的测试(红),再修(绿)——防止复发。
- 测试分层按项目基线:单元 / 集成 / 端到端;测试策略与报告归 `docs/testing/`。
- 测试不是门禁的全部,但没有测试的门禁一定过不了(见 `质量门禁.md`)。

### ⑤ 评审与门禁
交付前过**四道门**:构建通过 / 测试通过 / 静态检查(lint · typecheck,若项目有)通过 / **换另一个模型评审**(Codex 审 Claude,或反之)PASS。
**铁律:审稿模型 ≠ 产出模型**——错误不相关,等于免费质量倍增。门禁细节、失败处理与豁免规则见 `质量门禁.md`;结论写 `docs/reviews/` 或任务卡。

### ⑥ 发布与沉淀
- 版本发布走 `版本发布.md` 清单:门禁复核 → 版本号 bump → `flow/releases.md` 记变更日志 → tag / 发布物。
- 归档完成的任务卡;决策写 `flow/decisions.md`;**问题 / 解决 / 死路 / 踩坑写 `flow/踩坑记录.md`**;从中提炼的禁区 / 心智按 `文档维护SOP.md` 写进 `AGENTS.md`。

## 项目边界与分层

先判断协作边界,再运行六段循环。多个代码文件夹不等于多个项目:

- **单仓多子项目**:前端、后端、共享包等共享一个总体目标和仓库时,只在根级维护一套 `flow/`、`docs/` 和 hook。任务卡用产出路径区分模块,例如 `frontend/src/...`、`backend/src/...`。
- **独立仓库**:有独立 `.git`、版本、发布或团队边界时,每个仓库各自运行完整循环;上层总控仓库只记录跨仓目标、契约和集成交接。
- **子模块**:只有独立职责的模块才需要局部规则入口;普通脚本、构建产物和工具目录不建入口。

单仓多子项目的详细判断、文档位置和结构见 `多子项目结构.md`。

## 核心机制

### A. 进展日志 = 接力棒(Agent 接力的最小单位)
位置:`flow/进展.md`,**append、新的放最上面**。每个 Agent 干完一棒在顶部加一条;**顶部那条 = 当前交接棒**(`AGENTS.md` 开工必读它)。
每条字段:**做了什么 / 为什么 / 怎么理解 / 产出(路径)/ 门禁状态 / 问题→解决 / 下一步**。
- 一身三用:**可复制**(整条喂别的 Agent)、**可回看**(append 留全历史)、**能接力**(顶部即最新棒)。
- 收工时这条**既写进文件、也贴在回复里**——用户当场看到 + 可直接复制。
- 决策 → `decisions.md`,坑 → `踩坑记录.md`,产物 → `docs/`·代码目录(只给路径)。
- **「出方案 → 对照实现」**:A 把方案 / 契约写 `docs/contracts/xxx.md` 或 `docs/architecture/xxx.md`,进展条的"产出 / 下一步"带上该路径;B 顺路径打开照着实现,再写自己那条(实现中发现的缺口回填进文档)。

**铁律:只带「指针 + 增量」**——指向真实产出(给路径)+ 这一棒新增,**不重抄内容**;接手方要细节顺指针回源文件读。
(为什么是一个 append 文件,而不是 N 张卡或覆盖快照:N 张卡会堆爆;覆盖会丢历史、没法复制;append 一个文件 = 留历史 + 不爆 + 顶部即棒。)

### B. 分层入口 = 运行时合同
根级 `AGENTS.md` 是总体合同,写跨模块的精要规则、**门禁命令区(构建 / 测试 / lint 的真实命令)**、约束、目录地图和指针;根级 `CLAUDE.md` 软链到它。单仓多子项目中,每个有独立职责的模块再建局部 `AGENTS.md` + `CLAUDE.md` 软链,只补本模块职责、命令和约束。两个层级保持同源,让 Claude Code 与 Codex 在对应目录读取一致规则。

局部入口不能另起总体计划。根级 `flow/` 管整体推进,根级 `docs/` 管统一文档与契约,局部入口只把 Agent 导回这些真相源。

### C. 跨模型评审 + 质量门禁
Claude Code = 主控(持上下文 / 编排);Codex = 独立第二双眼睛。
模式:生成→评审 / 对抗找茬 / 第二意见。何时:每次交付前、高风险逻辑、设计岔路口。
评审只是四道门的最后一道;完整门禁定义见 `质量门禁.md`。**门禁状态必须如实记录**(进展条 + 任务卡),未跑就是未跑,不装绿。

### D. 契约先行(contracts = 模块间真相源)
- 跨模块接口先写 `docs/contracts/`(API 路径与字段、事件名与载荷、数据模型、错误码),双方确认后排任务。
- 改接口 = 先改契约文档,再改两端代码;契约与实现不一致时,**以契约为准修实现**,或走决策流程改契约——不允许代码悄悄偏离。
- 契约变更要在进展条里点名,让并行中的另一端及时知晓。

## 目录归属(R1)
| 文件夹 | 放什么 |
|---|---|
| 根级 `flow/` | 唯一控制层:charter / plan(契约)/ 进展(append 日志,顶部=交接棒)/ decisions / 踩坑记录 / releases(变更日志)/ tasks / 规范副本 |
| 根级 `docs/` | 集中内容层:`requirements/` 需求 · `architecture/` 架构 · `contracts/` 跨模块契约 · `modules/` 模块说明 · `testing/` 测试策略与报告 · `runbooks/` 部署运维手册 · `reviews/` 评审结论 |
| `<module>/`、`src/`、`scripts/` | 代码、测试、构建与运行配置;已有 README 或代码生成文档可就近保留 |
| 根级 `AGENTS.md` | 总体运行时合同(见机制 B),含门禁命令区 |
| `<module>/AGENTS.md` | 有独立职责子项目的局部合同;同目录 `CLAUDE.md` 指向它 |
| `DESIGN.md` | (可选)设计 / 创意决策 |

**判据**:协调 / 推进总体项目的 → 根级 `flow/`;需要统一发现的知识、契约和交付说明 → 根级 `docs/`;代码 → 对应子项目。默认不在子项目重复建 `flow/` 或 `docs/`。

控制层**指向**真实产出:任务卡 / 进展条里的"产出(路径)"可以是 `docs/contracts/...`、`frontend/src/...`、`backend/src/...` 等具体路径。已有局部 README、生成文档或必须跟代码同步的说明不强行搬家,但应从根级 `docs/README.md` 建索引。
