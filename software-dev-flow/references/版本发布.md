# 版本发布

> 定义"一版怎么发":范围确认 → 门禁复核 → 版本号 → 变更日志 → 发布动作 → 交接。
> 发布是一棒特殊的"收工",操作入口在 SKILL.md 操作 C。

---

## 1. 版本策略

- **项目已有版本规范则跟随**,不另起一套(初始化时已探测记录)。
- 没有规范的项目,默认**语义化版本** `major.minor.patch`:
  - 破坏性变更 / 大重构 → major
  - 向后兼容的新功能 → minor
  - 修 bug / 小调整 → patch
- 预发布可加后缀(`-rc.1` / `-beta.2`),正式版去掉。
- 版本号**集中写在一处**(常量 / 配置 / 清单文件),由它派生界面显示与产物命名,避免散落多处手动改。

## 2. 发布清单(按序走)

1. **定范围**:本次发布纳入哪些进展条 / 任务卡;未完成项明确排除并留到下版。
2. **门禁复核**:
   - 构建 / 测试 / 静态检查在发布分支或主线全绿;
   - 评审遗留项清零,或逐条列出豁免原因(用户确认);
   - 主线集成门跑过(见 `质量门禁.md` §5)。
3. **版本号 bump**:按 §1 规则递增;同一天多次发布只递增当日后缀或 patch,不跳号。
4. **变更日志**:在 `flow/releases.md` **顶部**追加一条(模板在文件里):版本 / 日期 / 类型(功能·修复·破坏性)/ 变更列表(用户视角,不是 commit 流水)/ 门禁状态 / 发布物。变更列表从任务卡和进展条汇总,按「新增 / 变更 / 修复 / 破坏性」分组。
5. **打 tag**:`v<版本号>`,tag message 引用该版变更日志首行。(项目有既定 tag 规范则跟随。)
6. **发布动作**:按项目类型执行——发包(npm / PyPI / crate…)、出镜像、部署、交付二进制。**以项目自身脚本和 `docs/runbooks/` 手册为准**,skill 不猜发布命令;手册缺失时先把本次发布步骤回填成 `docs/runbooks/release.md`,再执行。
7. **交接**:照常走收工交接(操作 B),进展条「产出」带上 `flow/releases.md` 和发布物路径;发布中踩的坑记 `flow/踩坑记录.md`。

## 3. 回滚

- 发布出问题:优先回滚到上一个 tag(能回滚是发布的基本要求),再修根因发 patch。
- 回滚也要在 `flow/releases.md` 记一条(类型标「回滚」),说清触发原因和恢复点。
- `docs/runbooks/` 里应有回滚步骤;没有就趁这次补上。

## 4. 原则

- **可追溯**:任何一个版本,能从 `flow/releases.md` 查到变更列表、门禁状态、对应任务卡。
- **变更日志写给人看**:写"用户会遇到什么变化",不是"改了哪些文件"。
- **发布不是终点**:发完照常交接,下一棒从进展日志顶部接上。
