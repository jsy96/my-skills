# software-dev-flow

把软件项目按清晰的**项目边界**来管理:**上下文落进文件,Agent 之间靠 `flow/`、`docs/` 异步接力;契约先行、测试同棒、门禁全绿才收工。** 本 skill 负责**搭建与维护这套开发协作结构**、**Agent 间收工交接(进展日志)**,以及**版本发布流程**。

- 完整方法论详规在 `references/`(`开发工作流程.md` / `初始化SOP.md` / `多子项目结构.md` / `文档维护SOP.md` / `质量门禁.md` / `版本发布.md` / `hook机制.md`)。
- 注入项目的模板实体在 `assets/templates/`。

## 先判断用户要哪个操作
- 要"初始化 / 接入 / 搭结构 / 建骨架" → **操作 A**
- 要"收工 / 交接 / 写交接卡 / handoff / 交接给下一个" → **操作 B**(在进展日志追加一条)
- 要"发版 / 上线 / 发布新版本 / 记 changelog" → **操作 C**(走发布清单)
- 拿不准就先问一句,别猜。

## 操作 A:初始化 / 接入项目

把当前软件项目接入开发流程,产出标准结构。**完整步骤与验证清单在 `references/初始化SOP.md`——执行前先读它。** 要点(对应非破坏原则):

1. **先判项目边界**:扫描代码入口、workspace 配置和嵌套 `.git`;判断单体项目、单仓多子项目,还是多个独立仓库。发现多个有独立职责的子项目时,先读 `references/多子项目结构.md`。不要仅凭文件夹数量判断。
2. **探测技术栈与真实命令**:从构建配置、包清单、CI 配置、Makefile / scripts 里读出**真实的**构建 / 测试 / lint 命令,填进根级 `AGENTS.md` 的「门禁命令区」。探测不到的留 TODO 占位并显式标注,**禁止编造命令**。
3. **判断状态**:目录是否已有 `AGENTS.md` / `flow/` / 其他协作骨架(含 project-flow-cy)。新项目全量铺;**已有项目非破坏合并(缺啥补啥,绝不覆盖已有内容)**;已接入过 project-flow-cy 的只补软件工程部分(门禁命令区、`质量门禁.md`、`版本发布.md`、`flow/releases.md`),不重建控制层。
4. **先列清单等确认**:把边界判断、探测到的命令和"将创建 / 修改的文件"列给用户,确认后再动手。
5. **铺根级骨架**:每个项目边界只建一套 `flow/`(`charter.md` `plan.md` `进展.md` `decisions.md` `踩坑记录.md` `releases.md` `tasks/`)+ `docs/`(软件版:`requirements/` `architecture/` `contracts/` `modules/` `testing/` `runbooks/` `reviews/`)。已有代码布局原样保留,不替 monorepo 猜造业务目录。
6. **生成分层入口**:用 `assets/templates/AGENTS.md` 生成根级 `AGENTS.md`(填入门禁命令区),再让根级 `CLAUDE.md` 指向它。单仓多子项目中,每个有独立职责的子项目用 `assets/templates/MODULE_AGENTS.md` 生成局部入口(Windows 软链改复制);局部入口只写本模块职责、命令、约束和根级指针。有 UI / 设计工作的项目可选建 `DESIGN.md`。
7. **装 hook**:只在项目边界根目录复制 `assets/templates/.hooks/`、`.claude/`、`.codex/`;`chmod +x .hooks/stop-devcheck.sh`。Claude Code 只以 `prompt_id`、可解析版本不低于 `0.145.0` 的 Codex 只以 `turn_id` 界定用户回合,每回合自动续跑一次;更旧、未知版本或缺 jq 时安全放行。细节见 `references/hook机制.md`。
8. **详规随项目**:把 `references/` 下 7 份详规复制到根级 `flow/规范/`(自包含)。
9. **跑接入自检**:在 Skill 源码目录运行 `bash tests/test-stop-hook.sh`,再逐项核对 `references/初始化SOP.md` 末尾清单。
10. **收尾**:引导用户填 `flow/charter.md`(含技术栈与质量基线);多子项目时一并确认子项目地图和 `docs/contracts/` 契约目录。

幂等:可重复跑,不产生重复或破坏(也是更新老项目详规副本的方式)。

## 操作 B:收工交接(在进展日志追加一条)

把当前会话这一棒的进展,**追加到 `flow/进展.md` 最上面**,供下一个 Agent / 会话接力。**一个 append 文件,不是一张张攒卡**;顶部那条 = 当前交接棒。

1. 在 `flow/进展.md` 顶部加一条(模板在文件里),填:
   - **做了什么 / 为什么 / 怎么理解 / 产出(路径)/ 问题→解决 / 下一步**(接手方第一个动作)。
   - **门禁状态**:本轮改了代码就要如实记——构建 / 测试 / lint / 评审各标 ✓ 或 ✗(未跑要写原因);没改代码标"本轮无代码变更"。
   - **并把这条同时贴在回复里**——用户当场看到 + 能直接复制给别的 Agent。
2. 决策追加 `flow/decisions.md`;问题 / 踩坑追加 `flow/踩坑记录.md`。
3. **铁律:只带「指针 + 增量」**——「产出」给真实路径,例如 `backend/src/...`、`docs/contracts/user-api.md`;不重抄内容。

## 操作 C:版本发布

**完整发布清单在 `references/版本发布.md`——执行前先读它。** 要点:

1. 确认发布范围:本次纳入的进展条 / 任务卡 / 里程碑。
2. **门禁复核**:发布前构建 / 测试 / lint 全绿,评审遗留项清零或明确豁免(用户确认)。
3. 版本号:项目已有版本规范则跟随;没有则按语义化版本 bump。
4. 在 `flow/releases.md` 顶部追加一条变更日志(版本 / 日期 / 变更列表 / 门禁状态 / 发布物)。
5. 按项目类型执行发布动作(tag、打包、部署……以项目自身脚本与 `docs/runbooks/` 为准),然后照常走**操作 B** 交接。

## 一直要守的铁律(来自方法论)
- **契约先行**:跨模块接口(API / 事件 / 数据模型)先落 `docs/contracts/` 并确认,再写实现;改契约先改文档。
- **测试同棒**:新代码与对应测试在同一棒交付;修 bug 先补一条能复现的测试。
- **门禁不过不收工**:构建 / 测试 / lint / 评审四道门全绿(或用户明确豁免)才算完成;红了不绕过。
- 审稿模型 ≠ 产出模型;产出落文件;先 plan 后 act,计划即契约;一会话一焦点;从根本解决不打补丁。
- **一个项目边界一个控制面**:单仓多子项目只保留一套根级 `flow/`、`docs/` 和 hook,不在子项目机械复制。
- **目录归属**:协调 / 推进项目的 → 根级 `flow/`;需要统一发现的知识、契约和方案 → 根级 `docs/`;代码 → 对应子项目目录。
- 需要展开规则时按需读 `references/` 下对应详规,别把全文塞进当前上下文。
